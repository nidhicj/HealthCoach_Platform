## 1. Scope

This phase replaces PHASE-02's rule-based, keyword-matched test recommendation with an LLM call that reads the Lead's actual questionnaire answers, and adds the mandatory HC review-and-send step the redesigned pipeline requires before any recommendation reaches a Lead (SPEC-0001 D-4, D-5). Concretely: a new LLM orchestration function, a real behavior change to the already-shipped `POST /api/intake/:slug` endpoint, two new HC-facing endpoints (the first in this codebase's `leads.py`, which doesn't exist yet), one new frontend review screen, and updated email functions.

**Not in scope** (explicitly deferred to later phases per the approved redesign plan):
- Payment (PHASE-05). This phase's "Send" action emails the Lead their finalized test panel, but **without** a payment/scheduling call-to-action — that CTA gets added when PHASE-05 ships, since the payment infrastructure doesn't exist yet. Document this clearly in the email so it doesn't read as a broken promise (no "click here to pay" link pointing at nothing).
- Scheduling handoff, upload token issuance timing change (PHASE-05) — this phase does **not** touch `lead_upload_tokens` at all. Upload token issuance moves out of the intake flow entirely (it used to fire immediately in PHASE-02) — PHASE-05 is responsible for issuing it after scheduling completes. This phase's modified `POST /api/intake/:slug` must stop issuing tokens, but does not need to issue them anywhere else yet.
- OTP-secured upload, two-part brief threading (PHASE-06).
- `hc_payment_accounts`, Razorpay account connection UI (PHASE-05) — not touched here.
- The Lead Detail page and the rest of `/api/leads/*` (list, patch, remind, convert, purge-expired) — still entirely unplanned, per SPEC-0001's Open questions. This phase adds exactly two endpoints under `/api/leads/:id/test-recommendation*` and nothing else to that namespace.

## 3. Decisions to carry into implementation

These are already made (SPEC-0001's Decisions log) — implementers should not re-litigate them, only implement them correctly:

- **D-4**: standard baseline stays deterministic, HC-configured, unedited by the AI or by this phase's review screen. Only `additions` are AI-drafted and HC-editable.
- **D-5**: no draft-save state on the review screen. The screen is stateless between visits except for what's already persisted in `draft_test_recommendation` (AI's output) — the HC's in-progress edits during a session live in frontend state only, discarded if they navigate away without clicking Send. Re-opening the screen re-loads the AI's original draft, not a half-edited version. (If SoJo wants edits to survive a navigation-away without an explicit save concept, that's a scope question to raise, not to assume — flag as a question if it comes up during implementation, don't silently add a persistence layer this decision explicitly avoided.)
- **D-7**: the draft/review artifact is never called a "brief" anywhere in code, comments, prompts, or UI copy — that term is reserved for the Stage 6 `lead_brief` artifact. Use "test recommendation" / "panel" consistently, matching the SPEC's own terminology discipline.
- The non-raising contract for `generate_lead_test_recommendation()` matters as much here as it did for `generate_lead_brief()` in PHASE-03 — this function's caller is `POST /api/intake/:slug`, a **public, unauthenticated, Lead-facing** endpoint. A Lead's questionnaire submission must succeed regardless of whether the AI drafting succeeds, exactly like PHASE-03's blood-report upload had to succeed regardless of brief generation. Treat this with the same rigor PHASE-03's Task 3 got (that task went through a real fix round for exactly this class of bug — a pre-`try` exception path that could still raise. Do not repeat it here.)

## 7. Bugs fixed mid-phase

- **Task 2**: `generate_lead_test_recommendation` looked up `HcLeadgenConfig` by the passed-in `hc_user_id` without reconciling it against the already-fetched `lead.hc_user_id` — a cross-tenant prompt-poisoning path on a public, unauthenticated endpoint (HC-A's test-panel config could be built into a prompt attributed to HC-B's Lead). Fixed with a one-line reconciliation raising on mismatch, caught by the existing outer `except`.
- **Task 3**: `all_tests` concatenation regressed the first-seen dedup the removed rule-based function had guaranteed; separately, the defensive `except` around `generate_lead_test_recommendation` didn't recover a dirtied session, so a swallowed DB-level failure inside that function's own non-raising contract could surface as an unguarded `PendingRollbackError` on the subsequent `db.commit()` — on a public endpoint whose `leads` row was already durably committed. Both fixed: dedup restored, and the fallback commit wrapped in rollback-then-retry, independently reproduced against real Postgres by the re-reviewer (not just asserted).
- **Task 5**: a docstring (and the implementer's own report) cited two sibling endpoints as precedent for "repeatable action, re-emails on repeat" — the "no already-sent guard" half was real, the "and it emails again" half was fabricated (neither sibling sends email at all). Corrected; the underlying idempotency decision (allow double-Send) stood on its own reasoning regardless.
- **Final whole-phase review** (a genuine cross-task composition bug no single task review could see): `GET /api/leads/:id/test-recommendation` never returned the already-sent `test_recommendation`, only `draft_test_recommendation` — reopening the review screen after a successful Send silently re-seeded the editor from the raw AI draft, and a second Send could overwrite an already-curated, already-emailed panel with different content. Fixed by returning `test_recommendation` from the GET, seeding the frontend editor from it when present, and adding a status guard rejecting Send once a Lead's status has moved past the reviewable window. Five accompanying minor fixes (stripped-not-stored test names, no length bounds on HC input, an inaccurate comment about commit/rollback expiry semantics, a silent retry-commit path, an empty-string `hc_name` edge case) closed in the same round. All independently re-verified against the diff by a second reviewer, not just the implementer's report.

## 8. Lessons learned

- **Cross-task composition bugs survive even when every individual task review is clean.** The reopen-then-resend bug above is the clearest example this phase produced: Task 5's reviewer correctly reasoned about double-Send in isolation (allow it — the HC may need to fix a typo), and Task 6's reviewer correctly reasoned about D-5 in isolation (always reload the AI draft, never a half-edited version) — both individually right, together wrong. Only the final whole-phase review, looking at the range across all 7 tasks together, could see it. This reinforces why the skill's final-review step is not optional busywork even when every task-level review came back clean.
- **Documentation debt compounds silently if not closed out as part of the phase itself.** By the time of the final review, this phase had let `docs/domain/glossary.md` drift out of sync with a retired mechanism (D-4), left its own `Status`/`Verification date` fields unset, and left SPEC-0001 asserting a fix ("PHASE-03's post-ship correction") that was never actually made in code. None of these were caught by any task-level review, because no task was ever scoped to touch `docs/`. Treating doc updates as the controller's own direct responsibility at phase close — not a follow-up task — is the fix; deferring it produced a real, shipped hallucination in SPEC-0001 that stood uncorrected for a full day.
